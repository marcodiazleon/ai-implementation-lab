## Third review of 8a079ea (Codex, 8/10 provisional): isolation boundary and promotion (T88, R58f, D57)

Finding V1 (P1, bounded to the runner): the supervisor that held the host export descriptor lived in the payload's PID namespace with the same identity, so the payload could reach that directory through `/proc/<pid>/fd`; the payload kept the capabilities of the namespace root, so the read-only probes before the payload did not prove immutability against a remount; the promotion followed links and validated neither type, links, names nor sizes, nor waited for every descendant.

Reproduced here before any change, with a dummy payload under the runner of 8a079ea (`sh` renumbers the descriptor opened as 9):

```
== fds of pid 1 (the supervisor):
   lr-x------ 1 root root 64 Oct 12 10:10 11 -> /tmp/claude-0/…/scratchpad/sbxp/export
== attempt: remount /usr read-write as namespace root
   remount rw SUCCEEDED: rw,relatime
== nested user+mount namespace: can the payload still remount?
   nested: remount rw denied (locked)
```

Fix (D57): three stages with three trust levels, described at the top of `scripts/sandbox/run_isolated.sh`; promotion by `scripts/sandbox/promote.py`. New controls printed before the payload: `fds` (no visible process holds a descriptor to a path outside the new root; the run's own standard streams excepted) and `isolation` (from a nested namespace identical to the payload's: remount refused, supervisor's descriptors and memory refused, no_new_privs set); after the payload: `promotion` (the PID namespace ended and the cgroup holds only the runner's own chain) and the `PROMOTED` line with the names and sizes copied. A second host uid for the payload was not needed once the owner of the export is outside the namespace: the supervisor is non-dumpable in its own user namespace and the payload has no capability over it, so `/proc/1/fd`, `/proc/1/environ` and `/proc/1/maps` are refused although both are kuid 0.

## HTTP hypotheses confirmed on an isolated server (R55a–b, D46, D51)

Before the change, an isolated server built from 86051b5 kept a handler thread for a client that sent `Content-Length: 60` and then nothing (no timeout; the connection stayed open until the client closed it), and an unlimited number of handlers could be busy at once. After the change: 408 REQUEST_TIMEOUT within the configured read timeout (C281, tested with a 1-second timeout), 503 SERVER_BUSY for the third request while two handlers are held open with a cap of 2 (C284), 400 INVALID_JSON for a body of 40,000 nested brackets that previously raised RecursionError inside the handler (C282), and 500 INTERNAL_ERROR without a message for an unexpected exception (C275). The server served normal requests after every refusal. After the review of 26fb88d: two idle connections (no headers) with a cap of 2 make a third connection receive `HTTP/1.0 503` on the socket with no handler thread created (C308); partial headers trickled every 0.5 s with a 1-second inactivity timeout and a 2-second deadline end in 408 at the deadline, and so does a body trickle (C309).
