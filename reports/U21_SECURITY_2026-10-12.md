## Sandbox used for every run (C306, R58e, D49)

`scripts/sandbox/run_isolated.sh SCRATCH -- COMMAND` refuses to run the command unless it has demonstrated each control. Observed on this machine (Linux 6.18 container, cgroup v1, util-linux `unshare` and `prlimit`):

| Control | Evidence printed by the script |
|---|---|
| pids | `cgroup pids.max=192` (256 for browser runs); probe forked 190 / refused 42 (254 / 42); cgroup `memory.limit_in_bytes=4294967296` |
| namespaces | user, mount, net and PID namespaces with a private `/proc`; the command dies with the namespace (`--kill-child`) |
| network | loopback raised by ioctl inside the namespace; `connect` to an external address and `getaddrinfo` fail (Errno 101) |
| target_ro | the repository bind-mounted read-only; a write probe fails with "Read-only file system" |
| scratch | tmpfs `size=1024m`, sticky, mounted over `/srv` inside the namespace; a 100 GB write is cut; the disposable copy, HOME and TMPDIR live there |
| env | `env -i` with PATH, HOME, TMPDIR, LANG, PYTHONUTF8, PYTHONDONTWRITEBYTECODE and, for browser runs, PLAYWRIGHT_BROWSERS_PATH, PLAYWRIGHT_SKIP_BROWSER_DOWNLOAD and NODE_PATH (9 variables) |
| limits | `prlimit --cpu=1800 --fsize=268435456 --nofile=1024` and `timeout` 1500–2400 s; the address-space rlimit (`SBX_AS`, default 6 GiB) is disabled for runs that start Chromium or Node (both reserve address space: Node's WebAssembly failed with "Cannot allocate Wasm memory" under it in the parity test), so memory is bounded by the cgroup limit of 4 GiB on those runs |

Two findings while building it, both fixed in the script: Chromium needs a private `/proc` in a new PID namespace, and it traps on start when TMPDIR is a path longer than a UNIX socket allows (108 bytes) or a non-sticky directory, so the scratch tmpfs is mounted sticky over a short existing path. Nothing was installed or downloaded; the implementer-side `setpriv` variant (dropping to an unprivileged user before the namespaces) was refused by the session's policy and is not part of the script.

## HTTP hypotheses confirmed on an isolated server (R55a–b, D46)

Before the change, an isolated server built from 86051b5 kept a handler thread for a client that sent `Content-Length: 60` and then nothing (no timeout; the connection stayed open until the client closed it), and an unlimited number of handlers could be busy at once. After the change: 408 REQUEST_TIMEOUT within the configured read timeout (C281, tested with a 1-second timeout), 503 SERVER_BUSY for the third request while two handlers are held open with a cap of 2 (C284), 400 INVALID_JSON for a body of 40,000 nested brackets that previously raised RecursionError inside the handler (C282), and 500 INTERNAL_ERROR without a message for an unexpected exception (C275). The server served normal requests after every refusal.
